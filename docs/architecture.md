# MT5889 Reverse Engineering Laboratory — Architecture Design

## 1. Project Goals
The MT5889 Reverse Engineering Laboratory aims to provide a deterministic, repeatable, and evidence-based approach to analyzing MediaTek (and similar) firmware. It leverages automated, reproducible experiments to uncover structures, validate findings mathematically, and build a unified understanding of the firmware layout. It accomplishes this while maintaining a zero-rewrite integration with existing `mstar_analyzer` logic.

## 2. Overall Architecture
The architecture consists of several core components working in concert:
- **Experiment Framework**: A suite of pluggable, independent experiments that interact with the firmware through a sandboxed context.
- **Evidence Engine**: A central authority that aggregates findings and manages their lifecycle (Candidate → Probable → Verified) by correlating multiple independent signals.
- **Hypothesis Tracker**: Resolves conflicts when evidence points to competing claims about the same structure.
- **MStar Adapters**: A layer that wraps existing `mstar_analyzer` capabilities into the structured Evidence Engine format without rewriting the underlying analysis code.
- **Storage Layer**: A SQLite database backed by JSON artifacts, designed to handle multiple independent firmware projects/sessions.
- **Reporting**: A generator for static, single-page HTML dashboards that embed all findings and allow interactive navigation.

## 4. Project / Firmware Session Model
The laboratory supports multiple firmware projects natively. Instead of a single global database, all analysis is scoped to a **Project** (or **Firmware Session**).
A Project encapsulates:
- Firmware metadata and configuration (e.g., SoC type, OS, layout hints).
- Extracted artifacts and payloads.
- Experiment results and execution history.
- The Evidence Database, Findings, and Hypotheses.
- Generated reports.
This enables the laboratory to analyze many different firmwares independently while reusing the same extensible experiment framework.

## 5. Experiment API
All experiments inherit from a base `Experiment` class that standardizes execution and output.
- **Attributes**: `experiment_id`, `display_name`, `version`, `requires` (dependencies), and `parameters`.
- **Methods**: `run(ctx: ExperimentContext) -> ExperimentResult`
- **Output**: Returns an `ExperimentResult` containing a status, summary, structured findings, artifacts dict, and metadata.

## 6. Experiment Context
A sandboxed `ExperimentContext` is provided to each experiment during execution.
It provides:
- Access to firmware and extracted payload paths for the current Project.
- Access to project-specific configuration.
- Read-only access to previous evidence via the Evidence Engine.
- `shared_data` containing explicit outputs from dependency experiments.
- Managed paths for writing local artifacts.
- Standardized logging and progress reporting.

## 7. Experiment Registry
The Registry manages all available experiments, their metadata, dependencies, and execution order. It prepares the `ExperimentContext` for each run by injecting the appropriate dependencies.

## 8. Automatic Experiment Discovery
The Experiment Registry uses automatic plugin discovery. It automatically scans the `mtklab.experiments` package (or designated entry points), validates the experiment modules, and registers them. Adding a new experiment only requires creating a new module containing a valid `Experiment` subclass—no central registry file needs to be modified.

## 9. Experiment Dependency Resolution
Experiments declare their dependencies via a `requires` attribute (a list of `experiment_id`s). The Registry performs a topological sort to resolve the execution order. If an experiment relies on the findings or artifacts of another, the Registry ensures the dependency runs first and injects its results into the current experiment's Context via `shared_data`.

## 10. Evidence Engine
The Evidence Engine is the central authority for tracking what is known about the firmware. Experiments do not modify the database directly; instead, they submit structured `Finding` and `Evidence` objects to the Engine.
The Engine manages a lifecycle of confidence:
- **CANDIDATE**: A single weak signal (e.g., a signature match).
- **PROBABLE**: Multiple independent signals converging on the same conclusion.
- **VERIFIED**: Mathematically proven (e.g., validated CRC, successful decompression).

## 11. Versioned Findings
The Evidence Engine preserves the complete history of findings and hypotheses instead of overwriting their state. When a finding's confidence is upgraded or a hypothesis is resolved based on new evidence, a versioned history is maintained. This allows the system (and analysts) to answer:
- Why did this become VERIFIED?
- Which experiment changed the confidence?
- What evidence existed before the change?
- How did competing hypotheses evolve over time?

## 12. Hypothesis System
When evidence conflicts (e.g., an entropy scan suggests one structure, but a signature points to another), the system tracks this as a `Hypothesis`.
- A Hypothesis tracks competing claims for a specific region.
- It links supporting and contradicting evidence to each claim.
- The status evolves (PROPOSED → SUPPORTED / CONTESTED / REFUTED → ACCEPTED) as more experiments contribute evidence, allowing the system to logically resolve contradictions once stronger evidence (like CRC validation) arrives.

## 13. SQLite Schema
The schema (instantiated per Project) supports the Evidence Engine, versioning, and lifecycle tracking:
- **`experiments`**: Tracks execution history, status, parameters, and metadata.
- **`evidences`**: Immutable records of signals submitted by experiments.
- **`findings`**: Structural discoveries (regions, objects). Includes a `status_history_json` column to store the versioned evolution of the finding.
- **`hypotheses`**: Competing claims, with associated evidence IDs and status, also tracking historical changes.
- **`experiment_artifacts`**: References to large files (JSON, CSV, plots) stored on disk.

## 14. Artifact Storage
Large datasets, plots, detailed logs, and extracted binaries are not stored directly in SQLite. Instead, they are saved as files in the Project's session directory (`data/projects/<project_name>/experiments/<exp_id>/`). The SQLite `experiment_artifacts` table stores references to these files, and standard JSON formats are used to ensure interoperability between experiments and the reporting layer.

## 15. HTML Reporting Architecture
The Reporting layer generates a static, single-page application (SPA) dashboard.
- **Zero Framework**: Uses vanilla JS and embedded CSS to ensure it can be opened locally without a web server.
- **Embedded Data**: All findings, evidence, and maps are injected into the HTML as a JSON payload during generation.
- **Interactive Components**: Features offset navigation (clicking an offset jumps to a hex view), cross-reference graphs (Evidence ↔ Finding ↔ Hypothesis), interactive entropy sparklines, a searchable evidence browser, and a collapsible experiment tree.

## 16. Execution Flow
1. **Initialize Project**: A new Firmware Session is created (`mtklab init-project <name>`).
2. **Configure**: The analyst supplies the firmware file and any known metadata in the project config.
3. **Run Experiments**: The CLI (`mtklab run`) invokes the Registry.
4. **Discovery & Order**: The Registry auto-discovers experiments, builds the dependency graph, and sorts them topologically.
5. **Execute & Store**: Experiments run sequentially, receiving sandboxed Contexts, yielding Results and Evidence to the Evidence Engine.
6. **Evaluate Confidence**: The Evidence Engine versions findings and updates confidence levels and hypotheses.
7. **Generate Report**: The CLI (`mtklab report`) queries the final state from the Project database and generates the interactive HTML dashboard.

## 17. Implementation Roadmap
1. **Core Infrastructure**: Project session management, SQLite schema with versioning support, Evidence Engine, Context, and auto-discovering Registry.
2. **MStar Adapter Layer**: Wrappers around `mstar_analyzer` logic (entropy, signatures, mapping) without modifying the original code.
3. **First 5 Experiments**: Implement `exp01` through `exp05` to validate the lifecycle from basic entropy scanning to complex CRC validation.
4. **HTML Dashboard MVP**: Generate the static SPA report with interactive tree, map, and evidence browser.
